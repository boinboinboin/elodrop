# Elodrop

Elo ratings for Norwegian badminton: singles, doubles and mixed doubles from tournament and league results since 2008 on [badmintonportalen.no](https://badmintonportalen.no), [Cup2000](https://www.cup2000.dk) and, for 2008–2014, [Profixio](https://www.profixio.com/app/tournaments), with rankings, player and club pages, head to head, the biggest upsets, Eliteserien team strengths and reviews, and draw luck in tournaments.

- `pipeline/`: the rating pipeline (Node scripts): fetches the results, rates them and exports the data the site reads. [`pipeline/README.md`](pipeline/README.md) is the full specification of the ratings and every feature.
- `web/`: the site (Next.js 16, React 19, TypeScript, Tailwind CSS v4), with the club content in Sanity.
- `.github/workflows/pipeline.yml`: runs the pipeline every night.
- [`CHANGELOG.md`](CHANGELOG.md): every version, with what was added or fixed.

## How it fits together

| What | Where |
|---|---|
| Fetched results, rankings, draws (raw input) | Cloudflare R2 bucket `elo-raw`; locally `pipeline/data` |
| Hand-edited input: `corrections.txt`, Eliteserien rosters, `organisers.txt`, `player-clubs.txt` | this repo, `pipeline/` |
| The site's data (rankings, players, clubs, upsets, Eliteserien, tournaments) | R2 bucket `elo-data`, public on `data.<domain>`; locally `pipeline/export` |
| Club content (names, regions, logos, home halls), halls, the season's tournaments' organiser and hall, and the players' badges (title, description, art) | Sanity (Studio at `/studio`; the nightly run adds the tournaments); `web/content/clubs.json` until Sanity is set up |
| User accounts (profiles, follows, ideas and votes, error reports) | Supabase (`supabase/`: the database, its rules and tests); off until its keys are set |
| The site | Vercel |

The pipeline writes plain JSON files (`pipeline/export.mjs`, at most 2 MB each). The site reads them on the server and caches them (`'use cache'`, tags `elo-data`, `elo-data:<area>` such as `elo-data:tournaments`, and one per file such as `elo-data/players/123.json`), until a tag is revalidated: not by time. After uploading, the nightly run sends `/api/revalidate` the files it uploaded or deleted (`pipeline/refresh-site.mjs`), so only the pages reading one of them are built again. Every page refreshed is an ISR write when it is next visited, and search engines crawl nearly every page, so old team matches, finished tournaments and players whose data didn't change stay cached. For the same reason no page reads a file that changes with every run for all of them: the footer's "updated" time and the badges' rarity on the player pages are loaded in the browser (`/api/updated`, `/api/achievement-stats`), and each player file has its own tournament links. Sanity's content is cached likewise, one tag per kind (clubs, halls, badges, each tournament: `web/data/sanityTags.ts`), so a change in the Studio refreshes only the pages showing it. A tournament's approval and a badge given by hand show at once (the webhook; a hand-given badge refreshes only its players' pages, one tag per player); clubs, earned badges and halls are each on thousands of pages, so the nightly run refreshes each kind once if any of it changed (`pipeline/sanity-revisions.mjs`). If a run's refresh of the site fails after its upload, the next run refreshes everything (a mark in the raw bucket), as it can't tell which files changed. A deploy very likely starts the pages' cache afresh, so every page visited after it is written again: merge several changes together, and not right after a full run if it can wait.

The nightly run fetches only what can have changed:

- **Tournament results**: a tournament once its end date has passed (end dates are remembered; rechecked on Mondays), and again each night for up to a week while badmintonportalen has no results for it yet. Until then, the matches played so far come from the tournament's draw (`pipeline/cup2000-results.mjs`), so a weekend's matches are rated the night after they're played.
- **Team matches**: a league group when one of its ties, by date, was played in the last 14 days and isn't in yet (results registered late). Mondays also list the groups again and sweep every ongoing group (postponed ties).
- **Tournament draws**: after the registration deadline, until the tournament has ended and been fetched once more for its final results. Sundays rescan the whole season.
- **Official ranking**: Wednesday to Friday, when it's published; the lists only when a new version is out.
- **Player register and clubs**: Mondays.
- **Birth years**: every night, for players not seen before.
- Raw files are kept between runs in GitHub's cache, so finished history isn't downloaded again.

Then it rebuilds only what's needed (`pipeline/fingerprint.mjs` compares the inputs with the last rebuild's):

- **full**: everything, and the pages whose data changed refreshed. The runs on Saturday, Sunday and Monday (01:15 UTC, after Friday's, Saturday's and Sunday's matches), manual runs, and any night when results (also ones registered late), the official ranking, the player register or the pipeline itself changed.
- **draws**: only new or changed tournament draws: just the tournament pages are uploaded and refreshed.
- **none**: nothing new: no uploads, and the site keeps its cached pages.

## The site's code (`web/`)

- `app/`: the pages and API routes (Next.js App Router); the site's pages are in `app/(site)`, the Sanity Studio in `app/studio`.
- `components/`: React components by area (`account/` for the user accounts' parts, `home/` for the front page's cards, `how-it-works/` and `whats-new/` for those pages, `players/`, `clubs/`, `rankings/`, `head-to-head/`, `tournaments/`, `upsets/`, `eliteserien/`), the header and footer parts in `layout/`, building blocks used everywhere in `ui/` (sections, cards, link tabs, badges, disclosures, buttons' classes), `charts/` and `format/`; `SVG/` has the icons, one per file.
- `data/`: reading the site's data: the cached loaders for the pipeline's export (one module per area, sharing `load.ts`) and the club content from Sanity (`sanity.ts`).
- `utils/`: functions used across the site: formatting (`format.ts`), the site's URLs (`hrefs.ts`), pools, ratings, rankings, tournaments, charts, sorting, the logo and the colour themes.
- `types/`: the shapes of the exported data.
- `app/(site)/how-it-works`: the ratings explained, in plain words and (with the "I'm a big nerd" switch) with the formulas; its text (`messages/en/how-it-works.json`) and numbers follow `pipeline/README.md`, so update it when the rules change. `app/(site)/whats-new` is `CHANGELOG.md`, read when the site is built.
- `messages/`: the site's text, one JSON file per area (`messages/en/`), read through `t()`, `plural()` and `rich()` in `messages/i18n.ts`. English is the only language so far; another (Norwegian) is a new folder with the same keys.
- The app: the site installs as an app (a Progressive Web App), so there's no separate app to build or keep in step: every change to the site is in the app too. Each language has its manifest (`app/[lang]/manifest.webmanifest/route.ts`, opening on that language's front page in its own window). The menu and the footer show "Install the app" where the browser can install it (`components/layout/InstallApp.tsx`, with `utils/install.ts` keeping Chrome's install offer from before the page has loaded), and on iPhone how to add it to the home screen. The only service worker (`public/sw.js`) is for push notifications (see "Notifications"), registered when a member turns them on: it has no fetch handler, so nothing is cached or fetched on its own, and it costs nothing. Browsers don't need one to install the site. Not in the App Store or Google Play: Apple doesn't take an app that is only a website, and Play would need its own listing.
- Written pages: About (`/about`) and Help & support (`/support`) are written in the Sanity Studio (Pages: one fixed document per page and language; `sanity/schemas/page.ts`), not in code. The content is rich text with blocks between its paragraphs: FAQ, image, person, button, note box, the site's numbers and an email address. `components/content/` renders it, a little more playfully than the rest of the site (`components/ui/Motion.tsx`, with the motion library; How it works, Achievements and What's new use its quiet parts: the title and the parts fading up). The English page shows the Norwegian one until it's written. The menu and the footer link to each page only once it's published (`app/api/pages`, loaded in the browser so the site's pages don't depend on it). Publishing refreshes that page at once through the Sanity webhook, whose filter must include pages: `_type in ["tournament", "page"]` (sanity.io/manage → API → Webhooks).

## User accounts

Signing in is optional: every page is the same for everyone and stays cached, and an account only adds things for its user. Signing in is by a code sent by email (typed on the site, so it works in the installed app too) or Google. With an account you can follow players and clubs (the star on their pages; the front page's Following card), say which player is you ("This is me": private, only you see it, and it gives you an overview of your own numbers), vote for ideas and suggest them (`/ideas`), and report a mistake about yourself.

- **No account is ever read on the server.** The pages don't read cookies, so they stay ISR pages, the same for everyone: everything about a user is a client component (`components/account/`) under `AccountProvider` (in the site's layout), talking to Supabase from the browser with the public anon key. The Supabase code is loaded only for a visitor who has signed in on that device, or on the account and ideas pages.
- **The rules are in the database** (`supabase/migrations/`): row-level security (each user reads and writes only their own rows), and triggers for what the site's code must not decide: the age limit, how often "This is me" can change, and the limits on suggestions and reports. `supabase/tests/accounts.sql` tests them (`pnpm dlx supabase test db` with the local stack running).
- **Age:** accounts are for 15 and over (`MIN_AGE` in `web/utils/account.ts`, and the `min_age` setting in the database). Norway's age for consenting on one's own is 13 today and 15 is proposed; from 15 no parent's consent is needed either way. The date of birth is asked for after signing in, without saying what the limit is; under it, no account is made and the sign-in is deleted at once. Only the birth year is kept.
- **"This is me" isn't verified**, so it's private: it changes only its user's own view (a false claim harms no one), and it can change once every 30 days.
- **Error reports** can only be about the reporter's own player, from an account at least 30 days old with a claim at least 14 days old: one open at a time, 3 in 90 days, at most 2 open about the same player, and two declined end reporting for that account (all checked by the database). They never go to GitHub issues, as the repo is public: the owner looks for new ones in the Supabase dashboard (Table editor → reports, status `open`), sets each to accepted or declined, and turns reports off with the `reports_enabled` setting (Table editor → settings). Closed reports are deleted after 12 months, by a nightly job in the database (`pg_cron`).
- **Ideas** wait for the owner: a suggestion (from an account at least 3 days old, 3 waiting at most; voting needs no wait) is shown once its status is set to open in the dashboard; planned and done move it on the page, declined hides it. Each shows its author's nickname (none once their account is deleted). New suggestions wait in the dashboard (Table editor → ideas, status `pending`), not on the site. An author can tick that the owner may email them about it (`contact_ok`); their address is in Authentication → Users, by the idea's `author`.
- **The overview** (the account page's first tab) is the member's own player's numbers that the player page doesn't show: the next tournament they're drawn in (found in the draws, with their group and chances), their last 4 weeks of matches, each season in review and their career and form. `app/api/players/[id]/dashboard` works them out (`web/utils/dashboard.ts`) and the CDN keeps each answer for 6 hours: the accounts' only cost on Vercel, a few runs a day per member at most; the Following card's ratings and latest results (`/api/players/<id>/summary`) are CDN-cached for a day, as the matches' route is.
- **Following** shows, besides the followed players' ratings, their draws coming up (`tournaments/drawn.json`), their latest results (the summary's `recent`) and the followed clubs' next and last team matches (`team-matches/clubs.json`): on the front page's card a few of each, on the account page all of them. The two files are read in the browser straight from the data bucket (`NEXT_PUBLIC_DATA_URL`, as EloStonk's players; locally, without it, from `/api/following/drawn` and `/api/following/clubs`), once per visit and only by a member following someone, so no page changes or costs more.
- **Bots** can't ask for sign-in codes: the sign-in form has Cloudflare Turnstile (Managed mode; free, no cookie banner needed), whose token Supabase checks with the request (Authentication → Attack Protection → CAPTCHA, with the widget's secret key). Its script loads only on the sign-in form (`components/account/Turnstile.tsx`, `NEXT_PUBLIC_TURNSTILE_SITE_KEY`). Google's sign-in has its own checks.
- **Trusted accounts** (`profiles.trusted`, set by the owner in Table editor → profiles; a user can't set it): their suggestions are shown at once, without the limits; their reports and their "This is me" skip the waits and caps.
- **Deleting an account** (account page) deletes the sign-in and every row of its user at once.

Locally: `pnpm dlx supabase start` from the repo root (Docker) runs the database with the migrations applied and prints its URL and anon key for `web/.env.local`; the emails, codes included, are at http://127.0.0.1:54324.

Migrations go to production with `pnpm dlx supabase db push` (the project linked). **Never edit a migration that's been pushed:** one recorded as applied is never run again, so the edit silently never reaches production (as with `*_elostonk.sql`, caught up by `*_stonk_catch_up.sql`). Add a new migration instead.

## EloStonk

The fantasy game (`/elostonk`, `components/elostonk/`; the rules in `pipeline/README.md`, "EloStonk"): members pick 5 players aged 18 or older, one the captain (counted twice), and score each round (Friday to Thursday) from how much better than expected their players do.

- **Data flow, with no new secrets:** the pipeline writes `elostonk/players.json` and the recent rounds' points (`elostonk/rounds/<Friday>.json`) with the rest of the export; Supabase imports them every night at 04:00 UTC from the data bucket (`stonk_import()`, a `pg_cron` job using the `http` extension, from `settings.data_url`). To import by hand: `select stonk_import();` in the SQL editor. The browser reads the players straight from the data bucket (`NEXT_PUBLIC_DATA_URL`): Cloudflare's traffic from R2 is free, so the game's biggest download (about 50 KB compressed: only what the page shows, each tournament named once) costs nothing on Vercel. That needs a CORS rule on the bucket (Cloudflare → R2 → elo-data → Settings → CORS policy): `[{"AllowedOrigins": ["https://elodrop.no", "https://www.elodrop.no", "https://localhost:3000"], "AllowedMethods": ["GET"]}]`. Locally, without the variable, it comes from the site's own route over the local export (`/api/elostonk/players`). Everything else comes from Supabase in the browser, so the page is static.
- **The rules are in the database** (`supabase/migrations/*_elostonk.sql`, tested in `supabase/tests/elostonk.sql`): a squad is saved for the next round only (the database decides which: `stonk_next_round()`), must be 5 different pickable players with the captain among them, at most 2 from one club (players without a club don't count; the `stonk_max_per_club` setting) and at least one man and one woman (the players' gender comes with the nightly import), and carries over until changed. The rules are checked when a squad is saved, so a squad saved before a rule came in keeps playing until it's changed; the picker checks them too (`components/elostonk/rules.ts`, in step). Everyone's squads, scores and the picks' statistics are shown by nickname only, and only once a round has locked (its Friday 14:00 in Norway). A save within 2 seconds of the last is refused (a brake on scripts).
- **Worked out ahead, not on every view** (materialized views, `stonk_refresh()`): the squads that counted and the picks' statistics every morning (04:30 UTC, after the import) and right after the lock (Fridays 13:05 UTC), the scores, the leaderboards and each member's standings after every round (their rank chart: `stonk_standings`) once a week (Mondays 04:45 UTC, with the weekend's results). A leaderboard reads only its top 100 and the member's own row. To refresh by hand: `select stonk_refresh(true);`.
- **Usernames** (the `nickname` column): unique whatever the capitals, one word of 3–20 letters, digits, `_`, `.` or `-` (`profiles_username_format`), changeable once every 30 days after a first free change (capitals alone any time; trusted accounts and the owner in the dashboard any time).
- **Moderation:** a rude username is hidden by setting `hidden` on the member's profile (Table editor → profiles): their ideas show without it, and they're left out of the leaderboards, leagues' tables and statistics. Words added to `blocked_words` (lowercase, matched anywhere) are refused in new nicknames and league names.
- **Leagues:** made by a member (at most 10), private (joined with an invite code or link) or public (`is_public`, chosen by the owner when making it and changed later: listed for everyone signed in by name and size, `stonk_public_leagues`, and joined with a press), at most 20 per member and 100 members per league. An invite code is 4 letters and digits without the look-alikes (no 0/O, 1/I; about a million codes, typed in any case, one box per character); as short codes can be guessed, an account gets 10 wrong codes an hour; a league without its owner passes to its longest member, an empty one goes. Each shows its last round's winner, its season table with the rounds each member won (`stonk_league_table`), each round's table (`stonk_league_round_scores`), the members' squads, and its most picked players in the round under way (`stonk_league_ownership`), all for its members only.
- **The team of the round** (statistics, and beside a member's own squad in their rounds): the best squad within the rules, found in the browser among the round's 30 best scorers (`components/elostonk/TeamOfRound.tsx`).
- **Cost:** a static page on Vercel and nothing per player; a handful of small files in R2 each night (only changed ones are written) and the players' file read from it (free traffic; R2's reads are free up to 10 million a month); Supabase's free tier, with the heavy sums done once a day or week.

## Notifications

A member who turns notifications on (account page, Settings: "Notifications", per device) gets one on their phone when a tournament draw on Elodrop first includes the player they've said is them ("This is me"): "You're drawn in Bodø Polarcirkel Cup 2026", with their events and groups, opening their overview. Once per member and tournament.

- **Where it works:** Android (and desktop browsers) straight from the site; iPhone and iPad (iOS 16.4+) only in the installed app (Add to Home Screen), which the account page explains with the site's install button.
- **The browser side:** `utils/push.ts` registers the push-only service worker (`public/sw.js`), asks for permission and subscribes with the public VAPID key (`NEXT_PUBLIC_VAPID_PUBLIC_KEY`); the subscription is saved in `push_subscriptions` (Supabase, the member's own rows; at most 10 devices).
- **Sending:** the Edge Function `push-draws` (`supabase/functions/push-draws`), called by the pipeline as soon as a run has published new draws and refreshed the site (`.github/workflows/pipeline.yml`, "Send notifications for new draws", with the Actions variable `SUPABASE_URL`), so a manual run in the day notifies at once too; and, as a fallback, every 30 minutes from 01:00 to 07:30 Norwegian time by the cron job `push-draws` (`pg_net`, `settings.functions_url`), while the nightly run publishes draws. It reads the data bucket's tournaments index, reads again only the draws fetched since its last look (`push_seen`), and sends to the subscribed members drawn in them not told yet (`push_sent`), encrypted and signed with nothing but Web Crypto (`webpush.ts`). A device whose subscription is gone is forgotten; a push service failing is tried again on the next call. Anyone may call it (`verify_jwt = false`): a call that finds nothing new does nothing.
- **Setting it up** (once): make a VAPID key pair (`node -e 'const c=require("crypto").createECDH("prime256v1");c.generateKeys();console.log(c.getPublicKey("base64url"), c.getPrivateKey("base64url"))'`); the public key into Vercel as `NEXT_PUBLIC_VAPID_PUBLIC_KEY`; the function's secrets: `pnpm dlx supabase secrets set VAPID_PUBLIC_KEY=… VAPID_PRIVATE_KEY=… VAPID_SUBJECT=mailto:<an address>`; and the function itself: `pnpm dlx supabase functions deploy push-draws`. To run it by hand: `curl -X POST https://<project>.supabase.co/functions/v1/push-draws`.
- **Cost:** none on Vercel; about 12 function calls a night, and one per pipeline run with new data, in Supabase's free plan (500,000 a month); a few reads from R2; the push services are free.

## Local development

Requires Node 26 and pnpm 12. Node 26 no longer ships Corepack, so pnpm is installed on its own, at the version in `package.json`'s `packageManager`. On Linux, Node 26 also needs `libatomic1` (`sudo apt install libatomic1` on Debian and Ubuntu).

Check that `node -v` says 26 before installing pnpm. Run under an older Node that had `corepack enable`, `npm install -g pnpm` fails with `EEXIST` on Corepack's own `pnpm` link.

```bash
nvm install && nvm use               # Node 26, from .nvmrc (or install Node 26 another way)
npm install -g pnpm@12.17.0          # the version in package.json's packageManager
pnpm install
# the data: run the pipeline (or copy pipeline/data from a previous run)
cd pipeline && node rate.mjs && node eliteserien.mjs && node upcoming.mjs --offline && node export.mjs && cd ..
cp web/.env.example web/.env.local   # set DATA_DIR=../pipeline/export
pnpm dev                             # https://localhost:3000 (see "Local https" below)
pnpm --filter web typecheck          # the types, with TypeScript 7 (as the build checks them)
```

To work with the same data as the live site instead, pull it from the buckets (needs rclone with a remote named `r2`, see below): `pnpm data:pull` copies the site's data into `pipeline/export` (what `DATA_DIR` reads), and `pnpm data:pull-raw` the latest fetched results into `pipeline/data`, so a local `rate.mjs` run starts from them. Or set `DATA_URL=https://data.<domain>` instead of `DATA_DIR` in `web/.env.local` to read the live data directly.

**Local https.** `pnpm dev` serves over https (`next dev --experimental-https`), as the live site does, so secure-only browser features (push, the service worker, secure cookies) behave the same. Its certificate is made with [mkcert](https://github.com/FiloSottile/mkcert) into `web/certificates/` (gitignored): on the first run Next downloads mkcert and tries to make it and trust it, which needs sudo on Linux. If that fails, it falls back to http; make the certificate without trusting it instead, and Next uses it from then on:

```sh
cd web && mkdir -p certificates && ~/.cache/mkcert/mkcert-v1.4.4-linux-amd64 -key-file certificates/localhost-key.pem -cert-file certificates/localhost.pem localhost 127.0.0.1 ::1
```

Then trust mkcert's root certificate (`mkcert -CAROOT` says where it is) in the browser's system. On WSL with a Windows browser, mkcert keeps it in `%LOCALAPPDATA%\mkcert`; in Windows, run `certutil -addstore -user Root "%LOCALAPPDATA%\mkcert\rootCA.pem"` once (no admin needed) and restart the browser. The origin is now `https://localhost:3000`: Supabase's local auth URLs (`supabase/config.toml`), the R2 CORS rule and Sanity's CORS origins name it.

Fetching everything from scratch takes hours (`fetch-players.mjs`, `fetch-clubs.mjs`, `fetch-portalen.mjs`, `fetch-league.mjs`, `fetch-ranking.mjs all`, `fetch-birth-years.mjs`); the nightly workflow only fetches what's new.

## Going live (on free plans, apart from the domain and Vercel Pro)

1. **Domain.** Buy one, e.g. through Cloudflare Registrar (sold at cost), so its DNS is on Cloudflare.
2. **R2.** In Cloudflare, create the buckets `elo-raw` and `elo-data`. Give `elo-data` the custom domain `data.<domain>` (public read). Create an R2 API token with read and write on both buckets.
3. **Seed the raw data** once from a machine that has `pipeline/data`, with rclone configured for R2 (`rclone config`, provider Cloudflare):
   `rclone copy pipeline/data r2:elo-raw --filter-from .github/raw-data.filter`
   and the web data: `rclone sync pipeline/export r2:elo-data --checksum`.
4. **Sanity.** Create a free project at [sanity.io/manage](https://sanity.io/manage) (dataset `production`), add the site's URL (and `https://localhost:3000`) as CORS origins, create a token with write access, then import the clubs:
   `SANITY_WRITE_TOKEN=... NEXT_PUBLIC_SANITY_PROJECT_ID=... pnpm --filter web import-clubs`.
   Add a webhook (API → Webhooks; on create, update and delete, drafts left out, filter `_type in ["tournament", "page", "badge"]`, projection `{ _id, _type, cup2000Id, "key": coalesce(after().key, before().key), "players": after().players, "playersBefore": before().players }`) to `POST https://<domain>/api/revalidate?tag=sanity`, with the header `Authorization: Bearer <REVALIDATE_SECRET>`, so approving a tournament refreshes its pages at once, and a badge given by hand (or taken) its players' pages and the achievements page. Clubs, badges earned by a rule and halls are on thousands of pages each (clubs on nearly every page, earned badges on every player page, halls on every team match page), so their changes wait for the night: the nightly run refreshes each kind once if any of it changed, and each tournament changed, in case its webhook call didn't arrive (`pipeline/sanity-revisions.mjs`). To show a club, earned badge or hall change at once: `curl -X POST -H "Authorization: Bearer <REVALIDATE_SECRET>" "https://<domain>/api/revalidate?tag=sanity:badges"` (or `sanity:clubs`, `sanity:venues`).
   Add the first badges (placeholder art, to change in the Studio): `SANITY_WRITE_TOKEN=... NEXT_PUBLIC_SANITY_PROJECT_ID=... pnpm --filter web import-badges`.
   For the nightly run to add the season's tournaments (`web/scripts/import-tournaments.mts`), create an Editor token for GitHub.
   For the Studio's preview of the written pages (the Presentation tool, "Preview" in the Studio's top bar), create a Viewer token: `SANITY_READ_TOKEN` in Vercel and `web/.env.local`.
5. **Vercel.** Import the GitHub repo with root directory `web` (its `vercel.json` skips building a push that changes nothing the site uses: only `pipeline/`, say), and set `DATA_URL=https://data.<domain>`, `NEXT_PUBLIC_SANITY_PROJECT_ID`, `NEXT_PUBLIC_SANITY_DATASET=production`, `REVALIDATE_SECRET` (any long random string) and `SANITY_READ_TOKEN` (the Viewer token, for the Studio's preview). Add the domain.
6. **GitHub.** In the repo settings, add the secrets `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `REVALIDATE_SECRET`, `SANITY_WRITE_TOKEN`, and the variables `SITE_URL=https://<domain>` and `SANITY_PROJECT_ID`. Run the Pipeline workflow by hand once to check it.
7. **Traffic watch.** Scrapers cost ISR writes (each uncached page they open is drawn and stored again), and the ones spread over thousands of home IPs get past robots.txt, the AI bots rule and rate limits. Every 3 hours the Traffic watch workflow (`pipeline/traffic-watch.mjs`) looks for networks opening uncached pages by the hundred without ever running the site's script (no analytics beacons), challenges them in Vercel's firewall, and opens an issue for each (closing it lets the network in again); it also keeps a per-IP rate limit and warns when ISR writes jump. Create a Vercel access token scoped to the team (Account Settings → Tokens; a token scoped to the project alone is refused for the traffic queries: "Observability query was rejected"), add it as the secret `VERCEL_TOKEN`, add the variables `VERCEL_TEAM_ID` and `VERCEL_PROJECT_ID`, and run the workflow by hand with "dry run" once to check it.

8. **User accounts** (optional: the site works without them). Publish the Privacy page in the Studio first (the sign-up links to it).
   - Create a free project at [supabase.com](https://supabase.com) (region Stockholm or Frankfurt) and apply the database: `pnpm dlx supabase link --project-ref <ref>` and `pnpm dlx supabase db push`.
   - Authentication → URL Configuration: the site's URL, and `https://<domain>/account` and `https://<domain>/en/account` as redirect URLs. Authentication → Emails: paste `supabase/templates/code.html` into "Confirm signup" and "Magic link", and set up SMTP with [Resend](https://resend.com) (free: 3,000 emails a month; Supabase's own sender only sends a few an hour).
   - Bots: in Cloudflare, Turnstile → Add widget (hostnames `elodrop.no` and `localhost`, mode Managed, pre-clearance off). Its secret key goes into Supabase (Authentication → Attack Protection → CAPTCHA, provider Turnstile), its site key into Vercel as `NEXT_PUBLIC_TURNSTILE_SITE_KEY` (and `web/.env.local` when working against the hosted project).
   - Google (optional): in [Google Cloud](https://console.cloud.google.com) → Google Auth Platform, the app's branding (name, home page, the Privacy page's link, `elodrop.no` as an authorized domain), audience External and published, and a Web application client: `https://<domain>` (and `https://localhost:3000`) as JavaScript origins, and the callback URL shown on Supabase's Google provider page (`https://<ref>.supabase.co/auth/v1/callback`) as the redirect URI. Its id and secret go into Authentication → Sign In / Providers → Google, then `NEXT_PUBLIC_SUPABASE_GOOGLE=1` in Vercel (and `web/.env.local`). Google's consent screen names `<ref>.supabase.co` until the branding is verified (free, a few days). A custom auth domain would hide it too, but that's a paid Supabase add-on. Supabase links a Google sign-in to the account with the same email, so someone who used a code before keeps their account.
   - In Vercel: `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` (Project Settings → API). The accounts appear with the next deploy.

### Plan limits that matter

- **R2:** 10 GB storage (the data is under 1 GB), 1 million writes a month: the pipeline uploads only files whose content changed (`rclone --checksum`), around 12,000 a night at most.
- **Vercel Pro:** a monthly fee with usage included, and what goes beyond it billed by use. What grows with crawlers is ISR writes (see Cost in `CLAUDE.md`), so pages are cached and refreshed only when their data changes, and most visits don't run any code. The firewall's rate limit is billed per request it lets through ($0.50 a million: cents a month here).
- **Sanity:** 10,000 documents per dataset; the clubs and their logos are about 270.
- **Supabase:** 50,000 monthly active users and a 500 MB database on the free plan; a free project is paused after a week without any requests (any signed-in visit counts).
- **GitHub Actions:** unlimited minutes on a public repo; a nightly run takes 5–20 minutes.
